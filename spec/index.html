PRODUCT SPEC / 产品规格

把能力做成产品，
先把边界写清楚。

这份公开规格说明 SOIA 如何从一个 Skill 逐层组合到工作流、插件、专家和私有仓库。它用于统一产品语言，不把尚未发布的功能说成现成产品。

PROBLEM

用户需要的不是更多工具名。

用户真正需要的是一个可以发现、安装、运行、验收和交接的能力单元；团队还需要知道哪些资料是公开的，哪些只能在授权范围内交付。

SUCCESS 01

看得懂

产品页面先说结果、输入、输出和边界，再说技术名词。

SUCCESS 02

装得上

公开能力有宿主入口、安装命令、版本和验证步骤。

SUCCESS 03

跑得通

组合能力拥有交接点、失败处理、人工批准和回执。

SUCCESS 04

分得开

公开仓库与授权资料隔离，私有交付不改变公开事实真源。

SCOPE

六种产品形态，
一条递进路径。

产品形态描述“交付什么”；课程描述“如何学会”；服务描述“如何共同落地”。

形态核心定义公开状态验收重点
Skill一个职责聚焦、可触发的任务能力Available输入、输出、边界
Workflow多个 Skill 的有序组合与交接Preview依赖、失败与人工批准
Plugin面向 Claude Code / Codex 的宿主安装包Previewmanifest、版本、安装
Expert面向 WorkBuddy 的角色、资料与任务入口Preview角色、权限、推荐任务
定制专家围绕授权 SOP 的私有组合ServicePilot、交付与维护
私有插件仓库团队内部的能力目录与发布通道Roadmap权限、版本、退出

DESIGN NOTES

每个形态都遵守四条规则。

01 / SOURCE

来源优先

公开说明链接到 GitHub 事实源；状态不确定时标记 Preview 或 Roadmap。

02 / HOST

宿主明确

Codex、Claude Code 和 WorkBuddy 是工作环境，不混称为模型。

03 / CONTROL

人保留控制

发布、付款、删除、权限和外部写入不默认自动执行。

04 / RECEIPT

交付可复核

输出、检查、限制和下一步形成回执，方便维护与交接。

ROLLOUT

先开放，再产品化，最后按范围落地。

发布顺序不是承诺时间表，而是降低不确定性的建设顺序。
