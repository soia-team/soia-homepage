让一个任务，从能做一次，到能够被团队反复使用。

这份规格定义 SOIA 如何把一个 Skill 逐层组合成 Workflow、Plugin、Expert、定制 Expert 与未来的私有插件仓库。它不把尚未发布的能力伪装成现成产品。

PRODUCT GOAL可发现、可安装、可验收
PUBLIC INPUT公开 Skill 与文档证据
PRIVATE INPUT经授权的 SOP 与资料
HOSTSClaude Code / Codex / WorkBuddy
RELEASE RULE先证据，后主张

问题

用户真正要的不是更多工具名，而是一种能被发现、运行、检查、维护和交接的能力。

当上下文、步骤、工具、验收条件只停留在聊天记录里，每次执行都像从零开始。团队无法知道哪个部分可公开、哪个部分需要授权，也无法把一次“看起来完成”的结果安全地交给下一位使用者。

“我们不把 AI 当作一句回答，而是当作一条有输入、有边界、有回执的工作路径。”

SOIA PRODUCT PRINCIPLE

范围与形态

产品形态回答“交付什么”；课程回答“如何自己构建”；服务回答“如何共同落地”。

形态核心定义公开状态验收重点
Skill一个职责聚焦、可触发的重复任务能力。Available输入、输出、边界和公开证据。
Workflow多个 Skill 的顺序、交接、批准与失败处理。Preview依赖、人工控制、可重跑回执。
Plugin面向 Claude Code / Codex 的宿主安装包。Previewmanifest、安装、版本和启停。
Expert面向 WorkBuddy 的角色、资料、工具和任务入口。Preview角色、可调用能力、权限与推荐任务。
定制 Expert围绕授权 SOP、模板与团队规则的私有组合。ServicePilot、验收、维护与退出方式。
私有插件仓库团队内部查找、安装、更新私有能力的目录。Roadmap权限、版本、发布与退出机制。

产品规则

无论能力以哪种形态交付，都必须满足下面四条可检查的规则。

01 / SOURCE

事实有来源

公开页面链接到仓库、规范文档与版本证据；无法确认的状态写 Preview 或 Roadmap。

02 / HOST

宿主说清楚

Claude Code、Codex 和 WorkBuddy 是不同工作环境。能力、模型与宿主不混称。

03 / CONTROL

关键决定留给人

发布、付款、删除、权限和外部写入需明确授权；可预览就先预览。

04 / RECEIPT

交付可以复核

结果包含产物、检查、限制和下一步，让后续维护与交接不依赖猜测。

建设顺序

这不是对时间的承诺，而是降低不确定性的产品化路径。

01 / OPEN

先公开

用真实公开 Skills 验证目录、安装、证据与安全边界。

02 / PRODUCT

再产品化

把 Workflow、Plugin 与 Expert 做成用户能理解的交付形态和规格。

03 / PRIVATE

最后按范围落地

仅在授权后把资料接入私有流程，用 Pilot 和验收完成交付。
