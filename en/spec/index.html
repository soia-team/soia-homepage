PRODUCT SPEC / PUBLIC

Turn capability into product.
Write the boundary first.

This public specification explains how SOIA moves from one Skill to a Workflow, Plugin, Expert, custom delivery, and a private registry. It keeps the product language clear without presenting an unreleased feature as ready.

PROBLEM

People do not need more tool names.

They need a capability unit that can be found, installed, run, accepted, and handed off. Teams also need to know which material is public and which can only be delivered with authorisation.

SUCCESS 01

Understand it

Lead with outcome, input, output, and boundary before technical names.

SUCCESS 02

Install it

Public capability has a host entry, install command, version, and check.

SUCCESS 03

Run it

Composed capability has handoffs, failure handling, approval, and a receipt.

SUCCESS 04

Separate it

Public repositories stay separate from authorised material and private delivery.

SCOPE

Six product shapes.
One progression.

Products describe what is delivered; the course describes how to learn; services describe how to land a private workflow together.

DESIGN NOTES

Four rules apply to every shape.

01 / SOURCE

Source first

Public pages link to GitHub evidence; uncertain status is labelled Preview or Roadmap.

02 / HOST

Host is explicit

Codex, Claude Code, and WorkBuddy are work environments, not models.

03 / CONTROL

People stay in control

Publishing, payment, deletion, access changes, and external writes are not automatic by default.

04 / RECEIPT

Delivery is reviewable

Outputs, checks, limits, and next actions form a handoff-ready receipt.

ROLLOUT

Open first, productise next, land by scope.

This is a build order for reducing uncertainty, not a promise of dates.
