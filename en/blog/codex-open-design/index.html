Codex × Open Design: from screenshot to working page

Open Design does not replace Codex. It turns visual references, design systems, and previews into design context that Codex can keep using.

August 2, 2026 · Guide · 8 min read

On this page

Division of workWorkflowUsing screenshotsProduction codeChecks

01 / ROLES

One holds design context. The other lands the result in the repository.

Open Design is the local design workspace for screenshots, visual direction, Design Systems, and previews. Codex reads project rules, understands existing code, implements pages, runs checks, and keeps iterating from browser evidence.

Key distinction: an Open Design prototype is visual evidence, not automatically production code. The shipped site still has to satisfy repository structure, accessibility, responsiveness, content boundaries, and release checks.

02 / WORKFLOW

Six steps from reference to delivery.

  1. Prepare real screenshots, target pages, brand content, and repository rules.
  2. Generate comparable page structures and visual language in Open Design.
  3. Set typography, color, spacing, components, and navigation interactions.
  4. Let Codex implement the accepted direction in shared CSS, JavaScript, and semantic HTML.
  5. Check desktop, mobile, and keyboard paths in a real browser.
  6. Run site validation for links, canonical URLs, language pages, and public boundaries before release.

03 / SCREENSHOT TO STRUCTURE

Screenshots provide structural evidence, not just pixels to trace.

A homepage screenshot sets navigation, fold proportions, and visual focus. Pricing establishes card density and emphasis. Catalog and detail screens define level-two and level-three hierarchy. Blog screenshots complete the content system.

Each screenshot should include what to preserve, what to replace, and what must not be copied. That produces a portable design language rather than a mirror containing another brand.

04 / PRODUCTION CODE

Shared components first. Product content second.

Header, mega menu, buttons, cards, detail sidebars, and article tables of contents should use one shared style and script layer. SOIA content then maps into those components without building a different visual system for every route.

Codex owns

Finding repeated structure, keeping changes scoped, preserving routes and SEO metadata, maintaining Chinese and English pages, and turning visual decisions into testable DOM, CSS, and interaction behavior.

05 / CHECKS

Visual similarity is only the first gate.

  • No horizontal overflow on desktop or mobile.
  • Mega menus work with pointer, keyboard, and mobile controls.
  • Each route has one main heading and one main landmark.
  • Internal links, language alternates, canonical URLs, and sitemap entries resolve.
  • No third-party branding, copy, screenshots, tracking code, or unlicensed assets remain.
